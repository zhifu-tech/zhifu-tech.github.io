KMP js vs wasmJs 核心区别

发表于 2025-12-24 分类于 技术笔记

KMP js vs wasmJs 核心区别

来源：ChatGPT
这是一个非常关键、而且在 KMP 项目里经常被混淆的问题。本文用「本质区别 → 能力对比 → 什么时候选 → 实际项目建议」四个层次来讲解清楚。

一、最核心的一句话区别（先给结论）

js 是"直接跑在 JavaScript 里的 Kotlin"
wasmJs 是"编译成 WebAssembly、再通过 JS 启动的 Kotlin"

两者都能在浏览器跑，但 技术路线完全不同。

二、本质差异（原理层）

维度 js wasmJs
编译产物 JavaScript WebAssembly（.wasm）+ JS glue
执行引擎 JS 引擎 WASM VM（由 JS 启动）
与 JS 互操作 ⭐⭐⭐⭐⭐（原生） ⭐⭐（有边界成本）
启动方式 直接加载 JS JS 加载 + WASM 初始化
技术成熟度 成熟稳定 仍在快速演进

三、能力 & 生态对比（非常关键）

1️⃣ 与 JS / Web API 的关系

js

  • ✔ 直接、无成本
  • ✔ 所有 Web API 都能用
  • ✔ Worker / DOM / Canvas / IndexedDB 完全友好

wasmJs

  • ❌ 不能随便 js("...")
  • ❌ Worker / DOM 要通过桥接
  • ❌ import.meta.url、npm 包支持很有限

👉 只要你依赖 Web API、npm、Worker，js 完胜

2️⃣ Worker / npm / 生态

能力 js wasmJs
Web Worker ✅ 完整支持 ⚠️ 受限
npm 包 ✅ 原生支持 ❌ 基本不可用
Vite / Webpack ✅ 成熟 ⚠️ 实验
import.meta.url ✅ ❌
sqljs / sqlite ✅ ❌

👉 你前面踩的坑，90% 都是 wasmJs 的限制导致的

3️⃣ 性能

场景 js wasmJs
UI / DOM ⭐⭐⭐⭐⭐ ⭐⭐
IO / Web API ⭐⭐⭐⭐⭐ ⭐
纯计算 ⭐⭐⭐ ⭐⭐⭐⭐⭐

👉 wasmJs 只在重计算场景有优势

四、Compose Multiplatform 下的现实情况（非常重要）

Compose Web 实际用的是：

目标 状态
js ✅ 主力、推荐
wasmJs ⚠️ 实验性 / 探索中

JetBrains 官方态度（总结）：

业务型 Web 应用：用 js
探索 WASM / 未来技术：试 wasmJs

五、什么时候该选哪个？（决策表）

✅ 选 js 的情况（你现在就是）

  • 使用 Compose Web
  • 使用 SQLDelight / sqljs
  • 使用 Web Worker
  • 使用 npm 包
  • 需要快速稳定交付

👉 90% Web KMP 项目都该选 js

🧪 选 wasmJs 的情况

  • 纯 Kotlin 计算逻辑
  • 不依赖 DOM / Worker / npm
  • 游戏引擎 / 算法 / 模型计算
  • 技术探索 / 原型

👉 极少数项目

六、为什么 KMP 默认"两个都给你"？

原因只有一个：

JetBrains 在为未来铺路，但你现在不一定要用

七、给你一个非常实际的建议（结合你踩过的坑）

✅ 如果你现在：

  • 遇到 import.meta.url
  • 遇到 Worker 报错
  • 遇到 npm 无法解析
  • 遇到 wasmJsTest 构建失败

👉 直接做这件事：

等 将来 wasmJs 真正成熟 再加回来。

八、一句话终极总结（送你）

js = 今天能用来赚钱的 Web
wasmJs = 明天可能很牛的 Web

九、WASM 的本质定位（深入理解）

来源：ChatGPT
这是个本质性的问题。如果只把 WASM 当成"跑得快的 JS"，那基本一定会踩坑。
本文用 「它是什么 → 它不是什么 → 它解决什么问题 → 为什么会被误解」 四步，把 WASM 的真实定位讲清楚。

一、WASM 到底是什么？（一句话定义）

WASM（WebAssembly）是一种"可移植的、沙箱化的、接近原生性能的低级执行格式"

拆开看这句话：

  • 可移植：一次编译，多平台运行
  • 沙箱化：安全、不能随意访问系统
  • 低级：接近机器指令，不是高级语言
  • 执行格式：不是语言，是目标格式（像 JVM bytecode）

👉 它不是一门语言，而是"目标平台"

二、一个关键类比（非常重要）

WASM ≈ JVM 字节码 ≈ LLVM IR

对象 角色
Kotlin Java
Rust / C++ C
WASM JVM Bytecode

👉 WASM 是"编译目标"，不是"开发体验"

三、WASM 不是用来干什么的（必须澄清）

❌ WASM ≠ Web UI 技术

  • 不能直接操作 DOM
  • 不能直接调用 Web API
  • 没有 UI 框架生态
  • 不适合业务逻辑层

👉 WASM 不是 React / Vue / Compose 的替代品

❌ WASM ≠ JavaScript 2.0

  • 不具备 JS 的动态能力
  • 不适合 IO / 事件驱动
  • 需要 JS 做胶水层

👉 JS 是 WASM 的宿主，不是对手

四、WASM 真正解决的是什么问题？

1️⃣ 把"原生计算能力"带进 Web

过去：

  • 浏览器只能跑 JS
  • C/C++ 算法没法复用

现在：

👉 Web 获得了"原生级计算能力"

2️⃣ 安全沙箱里的"原生代码"

WASM 特性：

  • 无指针越界
  • 无任意系统调用
  • 内存安全（可验证）

👉 浏览器敢跑 WASM 的原因

3️⃣ 跨平台分发"计算模块"

同一个 WASM 模块可以跑在：

  • 浏览器
  • Node.js
  • Serverless Edge
  • WASI Runtime

👉 WASM 是"计算模块的 USB 接口"

五、WASM 的正确架构位置（很重要）

正确分层模型

👉 WASM 应该在"最底层"

六、为什么 WASM 会被严重误解？

1️⃣ 宣传口径的问题

  • "Web 的未来"
  • "替代 JS"
  • "一次编写，到处运行"

👉 营销大于工程现实

你现在的场景：

  • Compose Web
  • SQLDelight
  • Web Worker
  • npm 包

👉 在这个系统里：

技术 角色
JS 宿主 & 控制
Compose Web UI
sqljs 数据层
Worker 并发
WASM ❌ 多余

八、未来 WASM 会不会"统治 Web"？

结论：不会

但它会：

  • 成为 Web 的 C / Rust
  • 成为 浏览器里的计算加速卡
  • 成为 Serverless / Edge 的基础设施

👉 不是应用层，而是基础设施层

九、一句"工程师级总结"

WASM 是 Web 的"CPU 扩展卡"，不是"操作系统"

十、WASM 在 2025 年的真实现状（工程视角）

来源：ChatGPT
这是个非常好的问题，而且你现在正好站在一个"被 wasm 各种宣传包围、但又被真实工程问题折磨"的节点上 😄
本文不讲概念，只讲现状、能不能用、什么时候该用。

一句话结论（先给你"工程视角"的答案）

WASM 现在是：底层能力已经很强，但"应用层生态还没跟上"
👉 适合"计算内核"，不适合"业务 Web 应用"

一、WASM 到 2025 年的真实现状（冷静版）

✔ 已经"成熟"的部分

1️⃣ 浏览器支持（没问题了）
  • Chrome / Firefox / Safari 全支持
  • WASM 性能稳定
  • 启动时间不断改善

👉 "能跑"这件事早就解决了

2️⃣ 性能优势（真实存在）

WASM 在这些场景明显强于 JS：

  • 数值计算
  • 图像 / 音频处理
  • 加密 / 压缩
  • 物理模拟
  • AI / ML 推理（非 GPU）

👉 "算得快"是真的

3️⃣ 语言生态（底层）
语言 成熟度
Rust → WASM ⭐⭐⭐⭐⭐
C / C++ ⭐⭐⭐⭐
Zig ⭐⭐⭐
Kotlin/Wasm ⭐⭐（快速演进）

二、但为什么你在 KMP 里感觉 wasm「处处是坑」？

因为 WASM 的"上层能力"非常不成熟。

三、当前 WASM 的三大硬伤（工程视角）

❌ 1️⃣ 没有"真实的 Web API 访问能力"

WASM：

  • ❌ 不能直接访问 DOM
  • ❌ 不能直接用 Web Worker
  • ❌ 不能直接 import npm
  • ❌ 不能直接 import.meta.url

必须：

👉 桥接成本高、复杂、不稳定

❌ 2️⃣ 生态是"碎的"

  • WASI（非浏览器）
  • WASM in browser
  • WASM + JS bundler
  • WASM + Node
  • WASM + Edge runtime

👉 每个场景一套规则

❌ 3️⃣ 应用框架几乎不可用

框架 WASM 状态
React ❌
Vue ❌
Compose Web ⚠️ 实验
SQL / IndexedDB ❌
Worker / ServiceWorker ❌

👉 WASM 不适合"业务 UI"

四、Kotlin / Compose / WASM 的真实情况（很重要）

Kotlin/Wasm 现在处于什么阶段？

Alpha / 技术预览 / API 不稳定

你已经亲身体验到了：

  • wasmJsTest 各种奇怪错误
  • Web Worker 完全不通
  • npm 包无法解析
  • import.meta.url 直接炸

👉 这不是你能力问题，是生态没准备好

✅ 最佳实践（业界共识）

实际案例

👉 没有一家用 WASM 写整个 Web App

会，但不是现在

未来关键技术：

八、给你一个"现实工程结论"

2025 年：

  • Web App：JS
  • KMP Web：js target
  • WASM：只做计算插件
  • Compose + wasm：别碰生产

九、最后送你一句"工程师视角金句"

WASM 不是 JS 的替代品，而是 C/C++ 的继任者

  • 对于业务型 Web 应用，应该优先选择 js 目标
  • wasmJs 目前更适合纯计算场景或技术探索

  • WASM 不是 JS 的替代品，而是 C/C++ 的继任者
